# CLAUDE CODE DIRECTIVE — Dry Run: Local llama.cpp + OpenCode Coding Agent on RTX 4060 8GB (Ubuntu, native Linux)

**This is a separate, standalone directive. It does NOT modify, replace, or reference-as-authoritative the RTX 5090 Windows/WSL2 directive. Its purpose is narrower: prove the core pattern — llama.cpp GGUF serving of a Qwen gated-delta-hybrid model + OpenCode + local search with optional Groq round-robin fallback — works end to end on hardware you already have, on Ubuntu, before attempting the same pattern on the friend's RTX 5090 Windows box. Treat this box's absolute decode speed as unimportant; treat "does the pipeline actually work, end to end, with clean fallback behavior" as the only thing that matters.**

You are Claude Code running on this Ubuntu laptop (Lenovo Legion 5, RTX 4060 8GB VRAM, native Linux — no WSL2 involved). Work phase by phase, verify before proceeding, log everything to `~/local-agent-bootstrap/INSTALL_LOG.md`.

## Target pattern (mirrors the reasoning validated for the RTX 5090 plan, scaled down)

- **Model:** a small dense Qwen gated-delta-hybrid GGUF — **`unsloth/Qwen3.5-4B-GGUF`** is the confirmed, available primary choice (Qwen3.5-4B is a genuine hybrid architecture: ~24 GatedDeltaNet layers interleaved with ~8 full-attention layers, same family lineage as the Qwen3.6/3.8-27B models targeted on the 5090, just far smaller — this makes it a real architectural dry run, not just "some small model"). If VRAM or RAM is tighter than expected, `unsloth/Qwen3.5-2B-GGUF` or `Qwen3.5-0.8B-GGUF` are same-family fallbacks. Verify current availability and recommended quant on Hugging Face before downloading — don't assume the exact repo/quant names above are still current.
- **Quant:** Q4_K_M as the baseline (per the owner's suggestion), but given how much VRAM headroom an 8GB card has relative to a 4B model, check whether a higher-fidelity quant (Q5_K_M, Q6_K, or Unsloth's UD dynamic quant) still leaves comfortable headroom — if so, prefer it; more quality at negligible cost is free money at this size class. Compute the actual VRAM budget (see Phase 3) before deciding.
- **Backend:** llama.cpp, native Ubuntu build (or reused prior build if the inventory finds one), CUDA. No Docker for the inference server itself — same reasoning as the 5090 plan: a native process is simpler to start/stop/reason about than a container.
- **KV cache:** `-fa on --cache-type-k q8_0 --cache-type-v q8_0`. Verify this model's native context length from its model card (smaller family members may not share the 262K of the 27B flagship — check, don't assume) and compute real KV budget from that.
- **MTP:** only if Unsloth (or anyone) ships an MTP-enabled GGUF for this model size — check, but do not block on it. MTP was already validated conceptually for the big-model plan; this dry run's job is the serving/harness pattern, not speculative decoding specifically. Skip cleanly if unavailable.
- **Harness:** OpenCode, same custom-provider pattern as the 5090 plan, pointed at the local llama-server endpoint.
- **Search:** SearXNG (reuse existing container if the inventory finds one; otherwise stand up fresh, same as before — JSON output must be enabled, it's off by default) + the same lean Rust scraper pattern (the `spider` crate + `article_scraper` for readability fallback) — **check the inventory first: hermes-max may already have a working scraper or MCP search setup; if so, reuse and just verify it, don't rebuild.**
- **Groq:** strictly optional, additive, never required — identical design to the 5090 plan. **This box's `.env` already has enumerated `GROQ_API_KEY_1`, `GROQ_API_KEY_2`, etc. from prior work — inventory what's there, verify the keys still work (or don't — testing the graceful-failure path with a stale/dead key is also useful data), and wire up the same round-robin-with-silent-fallback logic. Do not overwrite the existing `.env` — read it, extend it only if something's missing, never blow it away.**

## PHASE 1 — llama.cpp (native Ubuntu build, or verify existing)

If Phase 0 found an existing working build: verify it's current enough to support Gated Delta Net (`sched_reserve: fused Gated Delta Net (autoregressive) enabled` should appear at server startup with a hybrid model) and CUDA-enabled; if stale, rebuild.

If building fresh: confirm `nvcc`/CUDA toolkit present (`nvcc --version`); install via the distro's standard method if missing (apt or NVIDIA's official repo — check current recommended install path for this Ubuntu version rather than assuming). Then:
```
git clone https://github.com/ggml-org/llama.cpp.git
cmake -B build -DGGML_CUDA=ON -DCMAKE_CUDA_ARCHITECTURES=89   # RTX 4060 = Ada Lovelace, SM89 — verify this is still the correct value for current llama.cpp CMake conventions before running
cmake --build build --config Release -j
```
Confirm `llama-server --version` runs with CUDA backend reported.

**Verify:** a trivial smoke load (any tiny GGUF, or wait for Phase 3's real model) completes, VRAM shows in `nvidia-smi`, process exits cleanly with VRAM released on stop.

## PHASE 3 — Server config and launch

Compute real KV budget: (idle-free VRAM) − (weight file size) − (1-2GB safety margin for activations/desktop) = KV budget. Convert to token count using this model's actual per-token KV cost (compute it the same way as before: full-attention layers × KV heads × head-dim × 2 (K+V) × bytes-per-element at the chosen KV quant — get the real layer/head numbers from this model's config, don't assume the 27B's numbers apply). Pick `-c` accordingly, with real margin, not the exact computed ceiling.

```
llama-server
  --model ~/local-agent-bootstrap/models/<file>.gguf
  --n-gpu-layers 99
  -c <computed-context>
  -fa on
  --cache-type-k q8_0 --cache-type-v q8_0
  --np 1
  --host 127.0.0.1 --port 8080
  --jinja
```
(Add `--spec-type draft-mtp ...` only if an MTP-enabled GGUF was found and used in Phase 2.)

**Verify:** boots without OOM, `curl http://127.0.0.1:8080/v1/models` responds, log shows GDN fused kernel active, `nvidia-smi` VRAM usage matches expectations (weights + KV + small margin).

## PHASE 7 — The `agent` wrapper (bash, native Linux)

Simple bash scripts in `~/local-agent-bootstrap/bin/` (add to PATH via `~/.bashrc` or a symlink into `~/.local/bin`):

- **`agent up`** — starts `llama-server` in the background (nohup + PID file, or a systemd user unit if that fits this repo's existing conventions per Phase 0), starts SearXNG if not running, polls `/v1/models`, prints status (model, VRAM, endpoints). Idempotent.

**Verify:** fresh shell, `agent up` → live; `agent down` → VRAM idle; `agent code` in a scratch repo opens OpenCode.
